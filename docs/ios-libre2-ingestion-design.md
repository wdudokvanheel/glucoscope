## Current implementation boundary — 11 September 2026

The isolated store provides versioned Core Data model construction, a serial writer, session/clock validation, deduplicated reading-and-delivery transactions, explicit local-only delivery state, later deterministic destination assignment, redacted conflicts, committed snapshots, bounded explicit retry and injectable load/save/publication faults. Protected SQLite configuration is present for iOS; desktop SQLite tests cannot establish iPhone file-protection behavior. The completed synthetic suite covers injected faults, concurrent submissions, corrupt SQLite failure, reopen after SQLite saves and the actual commit stream. It exercises store operations directly and does not promote a decoder or create a production collection path.

Store operations remain serialized across each actor call through save and publication. Accepted dates are bounded to 2000–2100 and sensor minutes to 0–20,880; these are explicit ingestion-domain checks. Destination assignment freezes version-1 internal JSON for deterministic tests; it is not a Nightscout or Glucoscope backend payload adapter. Commit notifications are bounded hints to refetch committed data, not a durable replay log. Consumers must refetch on launch/reconnect and after missed notifications; historical notification replay is not guaranteed, including after a save succeeds but publication is interrupted.

In-process Keychain serialization and identity-preserving saves prevent an old BLE-held legacy value from erasing a migrated ID during a counter save. The stable fingerprint is a versioned SHA-256 of UID and stable patch bytes, excluding bytes 4–5 and pairing secrets.

Deliberate full NFC setup preserves UUID and the exact original clock only when physical identity, nonregressing sensor minute and lifecycle agree, and the new capture lies within 120 seconds of that clock mapping. This tolerance is an engineering repair policy, not a sensor-validated bound. Missing calibration/clock asks for read-only calibration; ambiguous continuity, backward minutes/lifecycle or a larger phone-clock correction blocks setup before pending credentials or streaming enablement. It never infers a fresh wear from clock disagreement alone. A different physical sensor receives a new UUID. Same-UID reset inference and reconciliation of a forgotten sensor remain unsupported. These new setup and Keychain paths have synthetic coverage only; existing v5 hardware evidence predates them.

`LibreVerifiedFrame` now carries the CRC-valid payload, receipt time, process sequence, generation and exact session/calibration/clock snapshot. The BLE queue resolves and saves a legacy wear identity before claiming a durable ID; an unavailable ID leaves only experimental diagnostics available. A synchronized gate rejects callbacks queued before stop, replacement, disconnection or calibration changes. Main-thread stop/setup/forget requests also invalidate ownership immediately. ## Boundary and flow

`LibreBluetoothCentral` now does short transport work on its existing serial queue: assemble, decrypt, and CRC-check a frame, then emit an immutable payload with its receipt time, connection generation, persistence session ID, and the exact identity/calibration/clock snapshot which authenticated it. An app-owned collection coordinator rejects a stale generation or replaced active session before invoking the pure decoder; it must never look up a newer pairing and relabel an older callback. In the future promoted path, it will submit only accepted slots to `ReadingStore` before canonical display, graphing or scheduling. The current production coordinator prepares metadata only and does not submit slots. `LibreStorageProbe` is a separate diagnostics-only service with separate foreground and locked fixture stores and cannot feed this path.

`ReadingStore` owns one serial Core Data writer context. One writer transaction resolves the sensor wear session, deduplicates every candidate, and creates both each new reading and its delivery record. Only a successful save publishes a commit containing the affected reading IDs. Local graph queries and the future upload coordinator consume that commit or refetch committed objects. Core Bluetooth never waits for network work, and SwiftUI never observes uncommitted candidates.

The committed local reading is the source of truth. Bluetooth collection, current value, graph and retained history must remain fully functional with no account, server, credentials or destination. Retain full-resolution history indefinitely by default when space is available; one year of minute-resolution data is a capacity-planning benchmark only. Any future purge must be a deliberate user action which first shows the date range, record count and delivery scope. Purging must not delete assigned pending/unacknowledged uploads, change frozen payloads, or alter deduplication and sensor-session identity. Disk-full behavior is an explicit storage failure, never an automatic purge.

A synthetic macOS capacity run through the current `ReadingStore.ingest` path, in batches of at most 512, stored 28 days of minute data: 40,320 readings, 40,320 unassigned delivery rows and two wear sessions. The closed SQLite file was 11,173,888 bytes, projecting to about 146 MB decimal (139 MiB) for 525,600 minute readings and their unassigned delivery rows over a year. Plan on roughly 150 MB/year plus variable WAL and operating-system overhead; this is not a guarantee or an iPhone measurement. The fixture contained no raw sensor packets, FRAM or upload payloads, and production ingestion remains unimplemented. `NSPersistentContainer` with `NSSQLiteStoreType` uses Apple's current Core Data SQLite engine; the app supplies its own model and transaction logic, not a custom SQLite engine.

The decoder promotion is a separate gate defined in [the decoder contract](ios-libre2-decoder-contract.md). The implemented engineering domain checks unrounded `20...600` mg/dL before one nearest-integer ties-away conversion; those engineering bounds align with storage and are not a qualified measurement range. Proposed live-state and clock/freshness behavior is documented in [the engineering policy](ios-libre2-live-state-clock-policy.md), and numerical evaluation is documented in [the evidence procedure](ios-libre2-decoder-evidence.md); both remain unqualified and unimplemented. Until numerical behavior has passing preregistered timestamp-matched evidence and the complete contract is qualified, `Libre2DiagnosticDecoder`, `Libre2DiagnosticFrame`, and `Libre2DiagnosticSlot` must not feed `ReadingStore`. Production ingestion should use a deliberately promoted decoder/result type so an accidental reference to the diagnostic path is review-visible. Diagnostic UI and exports may show an unpersisted calculation, but must label it experimental and must never expose it through `GlucoseMeasurement`, `DataSource`, the normal graph, or upload code.

## Core Data model for iOS 16.4

Use `NSPersistentContainer` with an SQLite store under a dedicated Application Support directory. Use an explicit model version and lightweight migration only for compatible additions; fail visibly rather than deleting or silently recreating an unreadable store.

| Entity | Fields and constraints |
| --- | --- |
| `StoredSensorSession` | `id: UUID` (unique), stable-identity fingerprint, sensor revision, first/last observed dates, lifecycle state, and non-secret clock provenance needed to interpret stored timestamps. It represents one physical sensor wear session, not one BLE pairing attempt. |
| `StoredReading` | `id: UUID` (unique), `sessionID`, `sensorMinute`, `sampleKind`, UTC sample date, received date, integer canonical mg/dL, quality, primary origin, observed-origin flags, decoder version, and creation date. Unique constraint: `(sessionID, sensorMinute, sampleKind)`. |
| `ReadingDelivery` | One required row per reading, unique by `readingID`; optional `destinationID`, state (`unassigned`, `queued`, `claimed`, `acknowledged`, `quarantined`), immutable payload/version once queued, attempt and lease fields, last error, and acknowledgement date. `unassigned` is the normal local-only state and is not an error. |
| `UploadDestination` | Stable ID, backend kind, normalized endpoint identity, credential reference, configuration revision, and enabled state. Credentials stay in Keychain. |

`sampleKind` is `trend` or `history15Minute` initially. BLE live/recovery slots and NFC trend slots share `trend`, so the same sensor minute deduplicates across those origins. Coarse NFC history remains a distinct internal kind. Graph queries prefer trend when both kinds cover the same minute and retain missing minutes as gaps; ingestion never interpolates. `origin` is provenance, not identity.

Store integer mg/dL as the canonical value and convert for presentation or backend contracts. Persist sensor minute because it is the stable sample coordinate. The UTC date is derived once from the validated session clock and retained for querying; timezone changes do not rewrite it. If a duplicate candidate disagrees with an already committed value or date beyond defined tolerances, retain the first canonical reading, record a redacted conflict diagnostic, and do not silently mutate an acknowledged or dispatched payload.

## Sensor wear identity and Keychain bridge

Add a random `persistenceSessionID` to the versioned Keychain `LibreSensorSession`. It survives calibration capture, peripheral changes, counter reservations, reconnects, and same-sensor pairing repair. `createdAt`, the peripheral UUID, unlock material, the full patch, calibration capture metadata, and clock recapture details are pairing/operation state and must not form the reading key. Stable physical identity comparison continues to use the UID and stable patch bytes, excluding mutable bytes 4–5.

Repeated full NFC setup can currently replace `createdAt` for the same physical sensor. Setup preserves `persistenceSessionID` only when stable identity matches and the sensor-minute/lifecycle evidence is consistent with the same wear session. A different physical identity creates a new UUID; ambiguous evidence for the same physical identity blocks repair rather than silently splitting the wear. Preserving the UUID must also preserve that session's original persisted clock anchor. A fresh setup capture must not move UTC dates for already known sensor minutes. A replaced sensor always creates a new UUID. Re-pairing a previously forgotten sensor may reconcile against retained Core Data metadata only under the same checks; this policy needs fixture and device validation before implementation.

Keychain and SQLite cannot share an atomic transaction. Reconcile them before accepting frames:

1. If a legacy Keychain session lacks an ID, generate one and save the upgraded Keychain record first. A failed Keychain write blocks ingestion.
2. On launch and before every ingest, upsert `StoredSensorSession` for that exact ID and verify its stable fingerprint in the Core Data writer transaction. Once present, the Core Data session clock is canonical for ingestion. Same-wear repair must copy that anchor back into the replacement Keychain pairing before frames are accepted; an unexplained clock disagreement is repair-required.
3. A crash after the Keychain save but before the Core Data insert is repaired by the next upsert. A crash before the Keychain save creates no durable ID and no reading. An ID/fingerprint disagreement is a repair-required error; never guess, merge rows, re-anchor an existing wear session, or ingest under the current pairing `createdAt`.

This bridge keeps pairing secrets and the unlock counter in Keychain with `AfterFirstUnlockThisDeviceOnly` accessibility while Core Data stores only the stable reference and non-secret reading metadata.

## Transaction and ordering rules

Each verified frame already receives a process-local monotonically increasing sequence before leaving the Bluetooth queue. The store accepts work through one asynchronous serial writer but does not reorder by sequence. The disconnected coordinator below now preserves source order and bounds backlog, but the Bluetooth transport does not feed it. The unique sample key makes delayed, repeated, overlapping or reverse-order frames with equal values converge to the same canonical samples. Conflicting values retain the first committed reading, so that choice depends on arrival order. The adapter uses only the guarded writer entry point rather than the generic direct/synthetic ingestion method.

Within one writer-context `perform` block and one save:

1. Resolve and validate the bridged sensor session.
2. For every accepted sparse slot, fetch `(sessionID, sensorMinute, sampleKind)`. Insert only missing readings; merge only non-canonical observation metadata on exact duplicates.
3. Create each inserted reading's required `ReadingDelivery`. If no destination is selected, save it as `unassigned` with no payload. If a destination exists, save it as `queued` with the destination and deterministic payload/version in the same transaction.
4. Obtain permanent object IDs, save once, then publish the committed IDs in chronological order. Roll back the context on any error and publish nothing.

Choosing the optional single Nightscout or Glucoscope destination later runs a separate transaction that converts eligible `unassigned` rows to `queued` and freezes their payloads. Setup may finish without a destination or credentials, and intentionally local-only readings must not inflate a delivery-error count. Future delivery claims use persisted leases and acknowledgements; those behaviors remain outside this ingestion milestone.

## Disconnected ordered coordinator — implemented engineering scaffold, 11 September 2026

`libre2-ordered-ingestion-v1` is implemented as disconnected engineering scaffolding in `LibreOrderedIngestion.swift`. The numbers below bound work and memory; they are not sensor cadence, freshness, recovery or accuracy guarantees. The app compiles this type without fixture flags but has no runtime caller. The current metadata coordinator keeps its existing one-replaceable-pending-frame behavior and zero candidates; runtime integration must retire it or explicitly reconcile its mutating preparation, pending policy and separate recovery budget with the canonical owner below.

| Decision | Required behavior |
| --- | --- |
| Ingress owner | One transport-owned mailbox accepts immutable frames synchronously on the serial BLE queue immediately after `makeFrame`, before any per-frame task or main-queue dispatch. Only this ordered producer may offer frames. A concurrent-caller API must serialize before sequence allocation/offer; sorting whatever has arrived later cannot restore a missing earlier callback. |
| Capacity | At most **8 retained frames total**, including the one active item and all pending items. Seven outcomes per frame means at most 56 potential slots, not 56 known candidates or new readings. Payload and captured session references held by active work count toward this bound. |
| Overflow | Reject the **newest offered frame** when full; retain the active frame and FIFO already admitted. Do not replace pending frames, split a frame, evict the oldest accepted work or silently coalesce glucose. Count the rejected frame with reason `backlogFull`. Sparse overlap may later recover some minutes; it is not guaranteed. |
| Sequence | Keep a process-lifetime `lastOfferedSequence`, updated for each current, strictly increasing offer even if capacity/state rejects it. Reject equal/lower sequences as duplicate/out-of-order before decode. Allow holes immediately: sequence allocation is process-wide and not every allocated frame reaches this consumer. Never wait for `last + 1`, fabricate a missing frame or infer lost sample counts from numeric gaps. |
| Work order | Exactly one drain worker processes the FIFO head through bridge, decode, private adaptation and awaited guarded-store completion before taking another item. No child task per frame and no parallel decode or pre-submission bridge. The active reservation persists until completion, including while suspended. Accepted candidates within one submission sort by ascending sensor minute; this never reorders frames. |
| Residence | Capture a monotonic enqueue instant at ingress. Reject a frame if more than **120 seconds** has elapsed before starting preparation, after any preparation await, or immediately before guarded submission. Exactly 120 seconds remains eligible for this engineering queue rule. It never changes the sensor-derived timestamp or establishes qualified sample freshness. There is no timer or forced interruption of an already submitted save; an active reference can remain until a stalled dependency returns, but still counts toward the fixed capacity. |
| Wakeups and telemetry | Coalesce to one scheduled/running drain signal; the signal must not capture each offered frame. Publish coalesced redacted counters/status, not one queued closure/log per overflow. Cap or coalesce retention across every diagnostic relay, including raw, verified and log events, so separate `main.async` streams cannot retain an unbounded number of payloads or full notification hex strings and defeat the mailbox limit. Preserve the existing diagnostic categories, useful latest snapshots and bounded counters, together with all production gates; retaining every event is not required. |

The current transport has three confirmed ordering/retention hazards. `appendNotification` emits `.rawFrame` before `frameGate.makeFrame` and `.verifiedPayload` after verification; `emit` independently queues both events on `DispatchQueue.main.async`. `didUpdateValueFor` also queues a full notification hex `.log`, and `.log` bypasses the generation filter. The canonical mailbox offer must therefore occur synchronously on the BLE serial queue immediately after `makeFrame` and before any asynchronous relay retains that completed raw or verified frame. Full-hex notification logging, including fragments received before a complete frame exists, must be capped/coalesced independently at its source. Preserve the existing diagnostic categories and useful latest snapshots/bounded counters. The existing `LibreCollectionCoordinator.receive` dropping non-increasing callbacks is not bounded ingress, and inserting a bounded array after `emit` is insufficient. Runtime connection remains gated on an explicit transport-handoff fixture and review.

Worker reservation and queue transitions must be synchronized in a short critical section, with no await, bridge/store call, decoder evaluation, user callback or generation-gate call under the mailbox lock. Check generation outside the mailbox lock and again at processing/submission boundaries; the revocable writer admission closes any race after the final check. Every invalidation path must use one operation order: revoke/activate the generation gate first, release its lock, then directly and synchronously purge the canonical mailbox before returning. Apply that same route to transport callbacks and main-actor stop, setup, calibration and forget actions; do not depend on an asynchronously emitted `.transportInvalidated` event for purge. This avoids a mailbox-to-generation/epoch lock inversion. An offer which raced the purge may be rejected at its next ownership check and still cannot commit. Clear pending work atomically with its discard accounting; an active transaction releases its reservation only when its own completion is known. Starting a new generation cannot start a second drain while that completion is outstanding.

On process relaunch there is an empty mailbox, fresh sequence bookkeeping and no replay of in-memory work. Reconnect, deliberate stop, replacement, calibration/clock snapshot change and forget invalidate old work through the unified revoke-then-direct-purge path above; do not reset the process sequence high-water mark on these transitions. Purge pending old-generation items, and let the active item either stop at a currentness check or finish the guarded writer's revocation decision. A successfully saved old-generation transaction remains history even if publication arrives after invalidation; its completion must never restore the old generation's readiness/current-value state. Foreground/background changes alone do not create a new wear or bypass the store/qualification gates.

### Canonical metadata prerequisite

The metadata-only `LibrePersistenceBridge.prepare` calls `ReadingStore.resolveSessionMetadata`, which may save **before** the bridge's post-await currentness check. A later stale-frame check cannot undo such a save. `ReadingStore` now blocks terminal-to-active lifecycle regression, but the existing mutating preparation remains unsuitable for candidate work. Runtime integration must retire that coordinator/path or reconcile it under the same canonical transaction and ownership rules; it must not run beside the candidate path as a second metadata mutator.

`LibrePersistenceBridge.prepareCandidates` implements the read-only preparation variant: it validates captured identity/clock, fetches existing canonical metadata without mutating it, and returns the exact per-frame session snapshot. For an existing wear it retains canonical clock, fingerprint, revision and first-observed date, requires lifecycle `.active`, and uses `max(stored.lastObservedAt, frame.receivedAt)` as observed date. For absent metadata it uses validated captured identity/clock with both observation dates equal to frame receipt. The guarded reading transaction alone inserts/updates this proposed metadata together with accepted readings and deliveries. Zero accepted slots produces no candidate-path metadata save. The existing metadata-only service remains separately identified; runtime integration must review its coexistence so it cannot bypass these rules.

Before connection, enforce lifecycle monotonicity at the writer: once a wear is `.ended` or `.replaced`, an `.active` proposal must fail with repair-required without changing that row, including if the lifecycle changed after read-only preparation. No captured callback can reopen a wear; supported deliberate repair must have its own reviewed transition and fresh activation. Preserve observation-date monotonicity and refresh the snapshot for **each frame**, rather than caching the first preparation of a generation and freezing `lastObservedAt`. Admission and decode bind that exact returned snapshot; the writer revalidates against current stored identity/clock/lifecycle. Required fixtures must cover stale preparation after replacement, terminal lifecycle changes between read and save, absent-session revocation with no metadata insert, successive frame observation dates and all-rejected no-save behavior.

### Failure, accounting and recovery decisions

Each frame has one terminal coordinator outcome. Count dropped undecoded frames separately from **known accepted candidates not committed**. An overflow, residence expiry before decode, stale callback, repair block or unavailable-store offer has an unknown accepted-slot count: report a frame count and optionally `7 × frameCount` explicitly as a potential-slot upper bound, never as lost readings. Decoder slot rejections have their own reason counts. After decoding, including residence expiry after mapping but before submission, accepted-but-uncommitted candidates can be counted exactly; these may still duplicate older canonical readings, so they are not a count of missing unique readings. Counters are bounded/saturating process-local summaries, not an unbounded per-frame log. Routine status contains operation, time, sequence, queue depth and reason without raw payload, UID, fingerprint, calibration, pairing secret or glucose.

| Outcome | Queue and recovery action |
| --- | --- |
| Whole-frame decoder rejection, all slots rejected, expired residence or stale ownership | No reading/delivery submission. Dispose of this item, record the applicable reason/count and continue with eligible FIFO work. Expected revocation leaves storage healthy. No retry of this frame. |
| Successful guarded call, including exact duplicate with no new IDs | Complete this frame once. New IDs and delivery rows exist only as committed by the store; empty IDs are not a failure. First successful arrival retains conflicting canonical values. |
| Adapter binding/version/shape mismatch or store `invalidInput`/`submissionMismatch` | Treat as an implementation invariant failure: pause this canonical consumer and flush pending frames, while diagnostics continue. Report a redacted invariant reason. Do not hide the issue with a generic-ingest fallback, per-slot salvage, repeated decode or automatic retry. Recovery needs a corrected implementation/new process. |
| Bridge identity, unsupported/missing clock or canonical-clock disagreement | Pause this consumer for repair and flush pending work. Continue discarding offers with a repair reason. Lifecycle events cannot repair/relabel a captured frame. Only a deliberate successful supported repair/setup followed by a fresh activation can resume; unsupported repair remains blocked. |
| Store load/fetch/save failure before durability | Store health/failure is authoritative. Count this frame's known accepted candidates only if decoding occurred, flush pending frames and pause canonical admission. No retained frame/candidate retry and no newer submission may overtake the failed active operation. BLE diagnostics may continue. |
| Save succeeded, publication failed | The store's `durableCommitAwaitingPublication` means the active candidates are already durable; count **zero** of them as uncommitted. Pause and flush later work. Retain only the at-most-seven deduplicated redacted sample keys from that exact transaction. After successful store recovery, verify that each key has exactly one reading and its required delivery before resuming; `retryAfterFailure()` currently returns no historical commits. Do not re-decode/resubmit the saved frame to recreate a notification. |
| Store recovery opportunity | One initial open plus at most **3** recovery attempts per process, bounded further by the store's own retry budget. Only explicit foreground-entry or deliberate reconnect opportunities may request one attempt; coalesce/ignore overlap with active work, with no timer, per-frame retry or reset on generation changes. Recovered health permits future offers only; it does not recover flushed frames. A publication failure additionally requires successful completion of its exact transaction-key storage checkpoint before resuming. This checkpoint is not graph/current-value refresh. Exhaustion remains visible until a new process; never delete/recreate the store or reduce protection. |

One launch-owned canonical service must own the initial store open and the single recovery budget across startup, bridge storage faults and publication faults; retire or reconcile the metadata coordinator's independent open/retry state so it cannot layer another loop over the store. Frames offered while the service is opening or unavailable are explicitly dropped and counted, never retained for replay after open. Classify stale bridge completion as expected revocation rather than repair. Check currentness after every await before publishing generation-specific readiness. A successful recovery need not have a current sensor, and must not manufacture one. Before first unlock or during unavailable storage, retain no waiting canonical backlog; subsequent ordinary frames may supply limited sparse recovery after a qualifying recovery opportunity. ## Protection, failure visibility, and recovery

Create the store directory with complete-until-first-user-authentication protection before loading the store and set `NSPersistentStoreFileProtectionKey` to the corresponding file-protection value on the persistent-store description. Validate on device that the SQLite file and its `-wal` and `-shm` sidecars inherit the same class. Any future file-backed upload batch must use that protection too. A reboot before first unlock is an expected unavailable-store state, not permission to hold readings indefinitely in memory or downgrade protection.

Store initialization, migration, bridge, fetch, constraint, and save errors become a main-actor collection status with operation, timestamp, redacted underlying error, and a dropped/uncommitted candidate count. Log the same redacted event through the existing diagnostics path. No failed candidate becomes a canonical reading. Stop accepting further canonical candidates while the store is unhealthy; allow BLE transport diagnostics to continue, retry store opening on a bounded lifecycle opportunity, and explain that sparse BLE recovery may recover some missed minutes but is not guaranteed. Never delete the store automatically.

## Meaningful implementation tests

Use an in-memory Core Data store for transaction semantics and a temporary protected SQLite store for migration/restart checks. Tests should prove:

- overlapping sparse frames, exact repeats, reverse arrival, and concurrent submissions yield one row and one delivery row per `(sessionID, sensorMinute, sampleKind)`, with genuine gaps left absent;
- BLE and NFC trend collide while NFC 15-minute history remains distinct, and graph selection prefers trend without rewriting history;
- no configured destination commits `reading + unassigned delivery` atomically, and later destination assignment queues all eligible rows exactly once with deterministic payloads;
- injected save/constraint/store-load failures publish no commit and expose an unhealthy status; a later retry does not create half a reading or orphan delivery;
- termination after Keychain ID migration but before the Core Data session insert, and termination after the Core Data save but before commit publication, reconcile without changing the session ID or duplicating readings;
- same-sensor setup repair, mutable patch bytes 4–5, pairing `createdAt` replacement, clock recapture, phone-clock/timezone changes, sensor replacement, and restart preserve or split session identity according to the rules above, with same-wear repair retaining both UUID and original clock;
- a delayed frame from an old connection generation or replaced sensor is rejected rather than decoded with the current pairing/clock or relabeled into its session;
- an acknowledged reading is immutable when a later candidate conflicts, and sparse recovery never manufactures a missing minute.

Fault tests need explicit save-failure injection and reopen of an on-disk test store; tests which merely call the same insertion method twice are insufficient. Hardware validation remains separate and pending: these tests cannot establish decoder accuracy, production-store behavior while locked, pre-first-unlock access, general background callbacks or behavior of untested sensor revisions.
